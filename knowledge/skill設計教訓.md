# Skill 設計教訓（2026-03～07 實戰）

版本：1.0 | 日期：2026-10-05

> 來源：spec-workflow skills（P1 規格消化 → P2 任務拆解 → P3 前後端實作 → PG 手測）用在 AR002、AR003、SO0062、GL026、eap TM002 等實際專案時發生的事件與事後審視。證據全在 [`history/`](../history/)。
> 用途：設計新 skill 前先掃一遍。每條都標明「問題有沒有被證實」和「解法有沒有被驗證」——這套 skills 在多數解法還沒驗證前就停用了，**不要把「設計了」誤讀成「有效」**。

## 怎麼讀

| 標記 | 意思 |
|---|---|
| ✅ 已證 | 有實際事件或數據證明問題存在／解法有效 |
| ⚠️ 未驗證 | 問題是真的，但解法沒在下一個專案驗證過就停用 |
| ❌ 推翻 | 曾經這樣做，後來證明是錯的 |
| 💭 判斷 | 審視時的推論，沒有量測 |

## 一、AI 拿到什麼就信什麼：權威來源要先定死

**1. 結構（資料表欄位、API 欄位）不能讓 AI 從既有程式碼推。**
- 問題 ✅：AR003 規格寫 17 欄、DDL 15 欄、真 DB 也缺 2 欄，AI 從旁邊的程式碼推 schema 全錯；GL010 從 stored procedure 推 schema 也出錯。
- 解法 ⚠️：用唯讀 DB 連線實際查表結構，產出一份當唯一權威；缺檔就停下回上一階段補，不准退而求其次去猜。
- 出處：[rationale](../history/spec-workflow-refs/rationale.md)、[04 D21](../history/04_通用型SKILL架構設計.md)

**2. 給「指針」不夠，要給「原文」。**
- 問題 ✅：GL026 D-01，任務清單只寫「見 A07」，公式在契約文件的備註欄。實作的模型把「跨 CHART_CODE 比較」做成「比公司」。
- 解法 ⚠️：有計算、比較規則的任務，必須逐字抄規格原文並註明出處，禁止改寫。
- 延伸：「附虛擬碼」被降為選配。虛擬碼是中間產物，前一步寫錯，後一步就會照著錯。逐字原文才是權威。
- 出處：[2026-07-03 審視 缺-1/缺-2](../history/review/2026-07-03/判斷力外部化審視.md)

**3. 形狀對了不等於意思對。**
- 問題 ✅：D-01 的欄位名、型別、巢狀層全對，對照表全過，但意思錯了。
- 更糟的是，欄位越是「計算出來的」（越容易誤解），形狀檢查越是空檢查。保護力和需要保護的程度剛好相反。
- 解法 ⚠️：實作前要求模型用一句話複述「比什麼、算什麼」，由人看一眼。
- 出處：同上

**4. 歷史程式碼可以查，但不能當規範抄。**
- 問題 ✅：AI 會複製既有程式碼裡的壞寫法。
- ❌ 推翻：v2.x 曾經「絕對禁止掃 code」。結果把查證所需的正當行為也一起禁掉了，而且與研究結論相反（用工具按需查找優於預先載入）。
- 改成：規範以專案文件為準；可以用 grep 查證既有寫法，PG 可以臨時指定一個好範本。
- 出處：[04 D26](../history/04_通用型SKILL架構設計.md)、[2026-05-29 導讀](../history/review/2026-05-29/README.md)

## 二、測試與驗證：先問「人眼幾秒看得出來嗎」

**5. Mock 測試是「自己出題自己答」，擋不住跨層錯誤。**
- 問題 ✅：AR003 有 4 支 API 前後端欄位不一致，SO0062 的後端已改成 camelCase；既有的 mock 契約測試全部通過，兩件都沒擋到。
- 原因：mock 資料和真實系統各自漂移。
- ❌ 推翻：v2 的「Processor 完整 TDD + 空值覆蓋」「前端契約測試」都已拔掉。
- 改成：前後端共讀同一份 API 契約，加上靜態對照表 ⚠️（對照表的攔截率沒驗證過）。
- 出處：[04 D19/D20](../history/04_通用型SKILL架構設計.md)、[lessons L-ARCH-06](../history/lessons_learned.md)

**6. UI、樣式、文字類寫單元測試幾乎沒有回報。**
- ✅ AR003：人眼 1 秒看出的問題，寫測試要 10 分鐘。
- 改成依任務類型分流：只有驗證邏輯走 TDD，UI 交給人工手測清單。
- ❌ 推翻：v1 的「統一 TDD」。

**7. 自動化驗證的基建成本，第一次導入最痛。**
- ✅ P4b（Playwright E2E）：一個 4 小時的 session 有 40% 耗在環境與來回切換；環境問題浪費 45 分鐘；同一個根因的 bug 拖了三輪。
- ✅ eap TM002 共 112 分鐘，66%（56 分 42 秒）卡在 P2 的整合測試基建（@QuarkusTest）、編碼問題與文件缺失。
- ❌ 推翻：P4a / P4b 整個廢除，改由 PG 照清單手測。
- 出處：[lessons L-ARCH-02](../history/lessons_learned.md)、[2026-05-29 導讀 §三](../history/review/2026-05-29/README.md)

**8. 「寫完才跑 typecheck」要用 hook 強制，不能靠叮嚀。**
- ✅ AR002 B03、AR003 B21/F11：測試該紅卻沒紅。
- 解法：commit 前由 hook 自動跑 typecheck 與模組測試，失敗就擋下並通知 PG，不讓 AI 自己修。依當時的試作比較，選定的方案（spike 3）能擋下這類事件；實際專案的誤報率和速度 ⚠️ 沒有量過。
- 出處：[04 D23](../history/04_通用型SKILL架構設計.md)

**9. 寫和審要分開，而且很便宜。**
- ✅ eap TM002 的獨立 Review Agent 只跑 5 分 42 秒，就抓到 4 個必修問題。112 分鐘的災難和寫審分離無關。
- ⚠️ 主線後來的「輕量獨立 review session」從沒驗證過。
- 出處：[2026-05-29 導讀 §三](../history/review/2026-05-29/README.md)

## 三、AI 的行動範圍：用清單框住

**10. 子 agent 不寫進 git 的程式碼。**
- ✅ session-791acadc：子 agent 寫程式碼時，prompt 與模板矛盾，4 個 Vue 檔全錯。
- 原因：子 agent 看不到主 session 累積的回饋，也沒有機會確認產出對不對。
- 子 agent 只做查找、跑指令、讀全文後回報摘要。
- 出處：[subagent-boundary](../history/spec-workflow-refs/p3/subagent-boundary.md)

**11. AI 會自己擴大範圍。**
- ✅ Insight 報告：35 次「做法不對」、12 次「改太多」。實例有 AR002Q 自己加了沒人要的匯出功能、順手重構相鄰程式碼、dialog 寬度被過度修改。
- 解法 ⚠️：動手前先寫三行範圍聲明（要交付什麼、預計動哪些檔、哪些不碰），超出就停下回報。這套「範圍聲明」有沒有真的攔到，沒有量過。
- 出處：[lessons L-ARCH-08](../history/lessons_learned.md)

**12. 邊界寫「清單」，不寫「原則」。**
- ✅ AR003：只寫「只修自己的 spec」這種原則，遇到灰色地帶的檔案（cleanup.ts、playwright.config.ts）就要逐項等授權。
- 改成直接列出「可動路徑 / 不可動路徑」。
- 出處：[lessons L-ARCH-04](../history/lessons_learned.md)

**13. 環境由人管理，AI 發現異常就停。**
- ✅ AR003：AI 執行 stash drop 蓋掉 DB 設定、自己 kill 掉 backend，浪費 45 分鐘。
- 出處：[lessons L-ARCH-05](../history/lessons_learned.md)

**14. 一次驗收多個元件會整批偏掉。**
- ✅ AR003 F20–F27：連續做完 8 個元件才驗收，全部偏了；AR002 一個 dialog 微調了 18 個以上的 session。
- 解法 ⚠️：前端硬性守則清單 + 每個元件做完就用 grep 檢查。
- 出處：[rationale](../history/spec-workflow-refs/rationale.md)

## 四、skill 本身的寫法：少即是多

**15. token 大頭常在「講話」，不在「做事」。**
- ✅ GL026 實測：P1（Opus）輸出 503K token，其中 65% 是只印在畫面、沒寫進檔案的敘述，context 峰值 286K。而 skill 裡「同一個 session 繼續做」這行指引，正是製造者。
- 解法 ⚠️：產出寫檔、畫面只留 10 行以內的摘要、步驟之間 /clear、規格書全文只交給子 agent 讀。
- 出處：[2026-07-03 審視 §0、缺-3](../history/review/2026-07-03/判斷力外部化審視.md)

**16. 執行檔裡的案例史是「注意力稅」。**
- 💭 P3 的 SKILL.md 估計有 30–40% 是理由、案例史和重複內容。執行的模型讀了案例史不會更守規矩，只會分散對真正指令的注意力。
- 改成：執行檔每條規則只留一行，「為什麼」集中放在 rationale 檔。
- 出處：[2026-07-03 審視 多-1](../history/review/2026-07-03/判斷力外部化審視.md)

**17. 一個關卡塞六件事，模型會做四件、漏兩件。**
- 💭 SG1 同時要求範圍聲明、載入報告、類型分佈、守則清單、hook 安裝選單和起始任務。後來收斂成三件。
- 出處：同上 多-2

**18. 沒人讀的紀錄就砍；兩條回饋管道等於沒有管道。**
- ✅ 每個 session 都自動歸檔對話紀錄，但從來沒人去讀；實際推動改進的是手寫的回饋檔。
- 回饋原本指定寫到家目錄，實際卻寫到專案 repo，最後統一成專案 repo 那一條。
- 出處：同上 多-5、缺-4

**19. skill 要有明確的結束點；維護期的修 bug 不進 skill 流程。**
- ✅ AR002 主輪結束後，ad hoc 修 bug 沒有留紀錄，這是健康的。反過來，硬要記錄只會讓進度檔膨脹、失焦。
- 出處：[04 D24](../history/04_通用型SKILL架構設計.md)

**20. 共用規則抽成一份，不要每個 skill 各抄一份。**
- ✅ 三個 P3 skill 重複了 30–40%，而且已經出現 README 與 SKILL 內容不一致。
- 出處：[04 D25](../history/04_通用型SKILL架構設計.md)

## 五、設計過程本身的教訓

**21. 規則的真正來源是事件，研究只是佐證。**
- ✅ 2026-05 審查發現：README 宣稱「每條規則都有量化研究支撐、不是經驗談」，但主線規則裡引用研究條目的次數是 0，依據全是實戰事件。
- 經驗驅動本身很健康，錯的是宣稱。
- 出處：[2026-05-29 導讀 G1](../history/review/2026-05-29/README.md)

**22. 新加的防禦要附「退場條件」。**
- ✅ 2026-05 審查：最後一輪的獨立批判抓到裁決方「砍多餘的手很穩，補缺口的手偏鬆」，對別人提的防禦用懷疑語氣，對自己提的新防禦用辯護語氣。
- 原則：攔截型的新防禦一律寫明「試用 N 個專案不達標就拔掉」。
- 出處：[2026-05-29 導讀 §五](../history/review/2026-05-29/README.md)

**23. 只列風險的檢查表，會系統性地多報缺口。**
- 💭 11 項行為風險只列「會出什麼錯」、不列「已經做對什麼」，拿它當尺去量，缺口判定會偏多。所以「缺口」應該當成值得查的方向，而不是必須補的證據。
- 出處：同上 G1

| 設計 | 想解決的問題 | 原定驗證方式 |
|---|---|---|
| 靜態對照表（契約 + 實際 DB schema） | #1、#5 | 手測階段的契約、schema 錯誤是否下降（W-05） |
| 規則原文 + 實作前複述 | #2、#3 | 下一個專案能否擋住 D-01 這類語意錯誤 |
| commit 前 hook | #8 | 誤報率、冷啟動速度、擋下後 AI 是否真的不自己修（W-06） |
| 範圍聲明 | #11 | 攔截次數、是否淪為走過場的儀式（W-07） |
| P1 子 agent 化 + 輸出紀律 | #15 | 前段 token 是否明顯下降（對照基準：P1 503K / P2 264K / P3 638K） |
| 輕量獨立 review | #9 | 限邏輯類任務先試 1 個專案 |
| 手測清單取代自動 UAT | #7 | 40–50 條測項的手測體感（W-03） |

## 這套設計的前提（重用前先確認還成立）

- **前提**：強模型（Opus）把判斷先寫進文件和關卡，較弱的模型（Sonnet 4.6）照著執行，「無從偏離」。
- **2026-10 回看**：
  - Anthropic 指出，harness 的每個元件都寫死了一個「模型做不到什麼」的假設，模型一變強，這些假設就會過期。
  - Claude 5 世代的指引方向是「規則改成判斷」。
  - 新 skill 若改由更強的模型執行，上面的關卡要逐條重新問：「它防的那個弱點，現在的模型還有嗎？」
  - 細節見 [`knowledge/LLM行為特性.md`](LLM行為特性.md) 與 [`review/2026-10-05`](../review/2026-10-05/研究更新盤點.md)。
